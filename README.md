# SmartBatch & FreshMargin AI

เครื่องมือช่วยร้านอาหารและเบเกอรี่รายเล็กตัดสินใจว่า "วันนี้ควรทำกี่ชิ้น" และ "ต้นทุนวัตถุดิบที่ขึ้นราคา กินกำไรไปเท่าไร" โดยไม่ต้องมีประวัติยอดขายย้อนหลัง

ต้นแบบสำหรับ AI for All Hackathon ธีม SME & Local Economy

- เว็บต้นแบบ: https://akirataiyo.github.io/SmartBatch-FreshMargin-AI/
- โค้ด: https://github.com/akirataiyo/SmartBatch-FreshMargin-AI

ตัวเลขร้าน ราคา และยอดขายทั้งหมดในต้นแบบเป็นข้อมูลสมมติเพื่อสาธิต ยังไม่เคยทดลองกับร้านจริง

## 1. ปัญหา

ร้านอาหารและเบเกอรี่รายเล็กเจอปัญหาสองข้อพร้อมกัน

**ต้นทุนวัตถุดิบสดขึ้นลงบ่อย** ราคามะนาว หมูสามชั้น ไข่ และเนยเปลี่ยนได้ทุกสัปดาห์ แต่ราคาขายปรับตามไม่ทัน โดยเฉพาะบนแอปเดลิเวอรี่ที่หักค่า GP ราวหนึ่งในสี่ถึงหนึ่งในสาม ร้านจึงขายดีแต่กำไรต่อจานลดลงโดยไม่รู้ตัว

**ของสดเก็บได้สั้น** ขนมและอาหารพร้อมทานเก็บได้ 1-3 วัน ทำมากไปก็ทิ้ง ทำน้อยไปก็เสียลูกค้า และร้านเล็กส่วนใหญ่ไม่มีบันทึกยอดขายเป็นระบบ โปรแกรมพยากรณ์ที่ต้องใช้ข้อมูลย้อนหลังหลายเดือนจึงใช้ไม่ได้

## 2. ผู้ใช้ที่ออกแบบให้

"พี่เล็ก" เป็นตัวละครสมมติ เจ้าของร้านเบเกอรี่และอาหารกล่องย่านออฟฟิศ ออกไปตลาดตอนตี 4 คุยกับลูกค้าทาง LINE จดยอดในสมุด ไม่ชอบโปรแกรมที่ซับซ้อน

สิ่งที่ต้องการ
- วางแผนผลิตรอบถัดไปได้ใน 3 นาทีบนมือถือ แม้ไม่มีประวัติยอดขาย
- เห็นกำไรต่อจานตามราคาวัตถุดิบล่าสุด
- เข้าใจว่าตัวเลขแต่ละตัวมาจากไหน

สิ่งที่ไม่ทำ
- ไม่ทำระบบ POS และไม่ต้องเปลี่ยนอุปกรณ์หน้าร้าน
- ไม่ทำ AI ที่ตอบตัวเลขโดยไม่อธิบายที่มา
- ไม่ให้ผู้ใช้กรอกข้อมูลละเอียดทุกวัน

## 3. วิธีคำนวณ

### จำนวนที่ควรผลิต

เมื่อไม่มีข้อมูลย้อนหลัง ระบบไม่พยากรณ์ยอดขาย แต่คำนวณจากสามอย่างที่เจ้าของร้านรู้อยู่แล้ว คือยอดจอง ของเหลือในสต็อก และขนาดรอบผลิตขั้นต่ำ (เช่น 1 ถาด = 24 ชิ้น)

```
ผลิต = max(0, ceil((ยอดจอง + เป้าลูกค้าหน้าร้าน - ของเหลือ) / ขนาดรอบ) x ขนาดรอบ)
```

ตัวอย่าง: จอง 20, เป้าหน้าร้าน 30, เหลือ 5, รอบละ 24 ชิ้น ได้ ceil(45 / 24) = 2 รอบ ผลิต 48 ชิ้น

### สามแผน

| แผน | เป้าลูกค้าหน้าร้านที่ใช้ | ความหมาย |
|---|---|---|
| เซฟ (Conservative) | 0% ของที่คาดไว้ | ทำตามยอดจองเป็นหลัก เสี่ยงขาดของ แต่แทบไม่เหลือทิ้ง |
| สมดุล (Balanced) | 60% | เผื่อลูกค้าหน้าร้านบางส่วน |
| รุก (Aggressive) | 100% | ทำเต็มตามที่คาด เสี่ยงเหลือทิ้งมากสุด |

ตอนประเมินกำไรและเงินจม ระบบสมมติว่าลูกค้าหน้าร้านมาจริง 70% ของที่คาดไว้ ตัวเลข 0 / 60 / 100 และ 70 เป็นค่าสมมติสำหรับสาธิต ยังไม่ได้ปรับจากข้อมูลจริง

### ต้นทุนและกำไรต่อจาน

- ต้นทุนวัตถุดิบคำนวณจากราคาที่ผู้ใช้ปรับ คูณปริมาณต่อจาน
- วัตถุดิบที่ต้องตัดแต่ง (หมูสามชั้นในเมนูข้าวหมูกรอบ) เผื่อส่วนที่ตัดทิ้งไว้ 25% เป็นค่าคงที่ในข้อมูลตัวอย่าง หน้าเว็บไม่มีช่องให้แก้ แต่แสดงไว้ในส่วน "ทำไมถึงได้ตัวเลขนี้"
- บวกต้นทุนอื่นต่อจาน (เครื่องปรุง กล่อง แก๊ส ค่าแรง) ที่ตั้งไว้ต่อเมนู
- กำไรเดลิเวอรี่คิดหลังหัก GP (ค่าเริ่มต้น 30%)
- เตือนเมื่อกำไรต่อจานต่ำกว่าเป้า (ค่าเริ่มต้น 40% ปรับได้ในหน้าเว็บ)

## 4. สิ่งที่ต้นแบบทำได้ตอนนี้

ไฟล์เดียว `index.html` เปิดด้วยการดับเบิลคลิก ไม่ต้องมี backend ไม่ต้องใส่ API key

**เครื่องคำนวณ 3 ขั้น**
1. วันนี้ของแพงขึ้นไหม: ปรับราคามะนาว หมูสามชั้น ไข่ เนย หรือเลือกชุดราคาสำเร็จรูป
2. วันนี้คาดว่าขายได้เท่าไร: ยอดจอง ลูกค้าหน้าร้าน ของเหลือ และขนาดรอบ
3. ผลลัพธ์: บอกเป็นประโยคเดียว เช่น "ผลิต 48 ชิ้น = 2 ถาด" เทียบสามแผนด้วยกำไรที่คาดและเงินจมถ้าขายไม่หมด พร้อมส่วน "ทำไมถึงได้ตัวเลขนี้" ที่แทนค่าในสูตรด้วยตัวเลขของผู้ใช้

มี 3 เมนูตัวอย่าง (ข้าวหมูกรอบ ครัวซองต์ ต้มยำ) ค่าที่กรอกถูกเก็บไว้ในเบราว์เซอร์ของเครื่องนั้น

เมนูเริ่มต้นคือข้าวหมูกรอบ ที่ราคาอ้างอิงกำไรต่อจานราว 36% ต่ำกว่าเป้า จึงเปิดหน้ามาพร้อมคำเตือนสีแดง ตั้งใจให้เห็นว่าระบบเตือนอย่างไร

**แชทตอบลูกค้า (เดโมจำลอง)**
ปุ่ม "ถามร้าน" มุมขวาล่าง ตอบจากคำสำคัญภาษาไทย ไม่ได้ใช้โมเดล AI เรื่องที่ตอบได้: เมนูวันนี้ ราคา ของเหลือ สั่งล่วงหน้า เวลาเปิด-ปิด ที่ตั้งและเดลิเวอรี่ ส่วนผสมที่อาจแพ้ อายุการเก็บ และขอคุยกับเจ้าของร้าน ราคากับจำนวนคงเหลือมาจากตัวเลขในเครื่องคำนวณเดียวกัน เปลี่ยนแผนผลิตแล้วคำตอบเปลี่ยนตาม

**อธิบายสถาปัตยกรรม AWS**
แผนภาพ ลำดับการไหลของข้อมูล ตารางประมาณค่าใช้จ่าย และแผนต่อยอด อยู่ในหัวข้อ "สถาปัตยกรรมคลาวด์ AWS สำหรับ SME" ท้ายหน้าเว็บ

## 5. สถาปัตยกรรมบน AWS (แผนสำหรับระบบจริง)

ส่วนนี้เป็นแบบที่ออกแบบไว้ ต้นแบบปัจจุบันยังไม่ได้เรียกบริการ AWS ใดเลย

```
มือถือ / LINE OA
      |
CloudFront + S3          หน้าเว็บ
      |
API Gateway
      |
   Lambda  ---------> DynamoDB      สูตร ยอดขาย สต็อก
      |
   Bedrock                          อ่านรูปใบเสร็จตลาด / ตอบแชทลูกค้า
```

| บริการ | หน้าที่ |
|---|---|
| CloudFront + S3 | เก็บและส่งหน้าเว็บ |
| API Gateway | รับคำขอจากหน้าเว็บและแชท |
| Lambda | คำนวณแผนผลิต ดึงข้อมูล เรียก Bedrock |
| DynamoDB | เก็บสูตร ราคาวัตถุดิบ ยอดขาย และของเหลือทิ้ง |
| Bedrock (Claude Haiku) | อ่านรูปใบเสร็จตลาดสดเพื่อดึงรายการและราคา และตอบแชทลูกค้า |

ช่องทางแชทลูกค้า (ระยะที่ 2): ลูกค้าถามผ่าน LINE OA หรือเว็บแชท ไปที่ API Gateway และ Lambda ซึ่งดึงเมนู ราคา และจำนวนคงเหลือจาก DynamoDB แล้วให้ Bedrock เรียบเรียงคำตอบ

ทุกบริการคิดเงินตามการใช้จริง ไม่มีเซิร์ฟเวอร์เปิดทิ้งไว้

**ค่าใช้จ่ายต่อร้านต่อเดือน (ประมาณการ ยังไม่ได้วัดจากการใช้งานจริง)** สมมติใช้วันละ 20-50 ครั้ง

| บริการ | USD |
|---|---|
| CloudFront + S3 | 0.075 |
| API Gateway | 0.100 |
| Lambda | 0.050 |
| DynamoDB | 0.075 |
| Bedrock | 0.200 |
| รวม (ไม่เกิน) | 0.50 (ราว 18 บาท) |

ค่าจริงขึ้นกับปริมาณการใช้ โดยเฉพาะ Bedrock ที่คิดตามจำนวนรูปและข้อความ

## 6. คำถามที่ตรวจสอบระหว่างออกแบบ

| คำถาม | ความเสี่ยง | วิธีรับมือ |
|---|---|---|
| ไม่มีประวัติยอดขาย จะเอาตัวเลขมาจากไหน | ถ้าระบบทายมั่ว ร้านทำตามแล้วเสียหาย | ไม่ทำนาย ใช้ยอดจอง สต็อก และขนาดรอบ แล้วให้เลือกสามแผน พร้อมอธิบายสูตร |
| ร้านไม่มีเวลากรอกราคาทุกวัน | ผู้ใช้เลิกใช้ | ปรับเฉพาะราคาที่เปลี่ยน มีชุดราคาสำเร็จรูป ระยะที่ 2 ถ่ายรูปใบเสร็จแทนการพิมพ์ |
| ใช้ Excel ฟรีก็ได้ไม่ใช่หรือ | ไม่มีเหตุผลให้เปลี่ยน | Excel บนมือถือกรอกยาก ไม่ปัดตามขนาดรอบอัตโนมัติ และไม่เตือนเมื่อกำไรต่ำกว่าเป้า |
| ถ้าต้องทำเป็นรอบ เช่น 1 ถาด 24 ชิ้น | ตัวเลขเป็นเศษ ใช้จริงไม่ได้ | ปัดขึ้นตามขนาดรอบ และแสดงจำนวนที่เกินและเงินจมที่เสี่ยง |

## 7. สิ่งที่ยังไม่ได้ทำและข้อจำกัด

- ข้อมูลร้าน ราคา และยอดขายเป็นสมมติทั้งหมด ยังไม่ได้ทดลองกับร้านจริง
- ค่า 0 / 60 / 100% ของแต่ละแผน และสัดส่วนลูกค้าหน้าร้านที่มาจริง 70% เป็นค่าสมมติ
- แชทเป็นระบบจับคำสำคัญ ไม่ใช่โมเดล AI ตอบได้เฉพาะเรื่องที่เขียนกฎไว้
- ยังไม่ได้เชื่อม AWS, LINE OA หรือฐานข้อมูล ข้อมูลเก็บในเบราว์เซอร์ของเครื่องที่ใช้
- ราคาค่าใช้จ่าย AWS เป็นประมาณการ
- ทดสอบด้วย Microsoft Edge เท่านั้น ยังไม่ได้ทดสอบบนมือถือจริง หรือกับโปรแกรมอ่านหน้าจอ
- เป้าหมายที่ตั้งไว้เพื่อวัดตอนทดลองกับร้านจริง (ยังไม่มีผล): ลดของเหลือทิ้ง 35% ใน 30 วันแรก วางแผนหนึ่งรอบได้ภายใน 3 นาที

## 8. แผนต่อยอด

1. **ระยะที่ 1 ต้นแบบ** เปิดเว็บผ่าน CloudFront + S3 ทดลองกับร้านอาหาร 10 ร้านในชุมชน เพื่อดูว่าเข้าใจและใช้ได้ภายใน 3 นาทีหรือไม่
2. **ระยะที่ 2 LINE OA + Bedrock** ส่งรูปใบเสร็จตลาดสดทาง LINE ให้ Bedrock ดึงราคาเข้าระบบ และเพิ่มแชทตอบลูกค้าจริง
3. **ระยะที่ 3 ราคาอ้างอิงระดับย่าน** รวมแนวโน้มราคาตลาดสดในแต่ละย่านเพื่อเตือนล่วงหน้า เช่น มะนาวมีแนวโน้มแพงขึ้นในสัปดาห์หน้า
